## 原文（日本語訳）

`Bash(ls*)` のようにワイルドカードを直接付けたBash許可ルールが、場合によって権限確認をスキップしていた問題を修正しました。`Bash(NODE_ENV*)` のように変数名を指定するルールは、確認を求めるようになります。また、`*` を変数の値に含む許可ルール（例: `Bash(PORT=* npm run dev)`）には起動時に警告が表示されます。

## 原文（英語）

Fixed Bash allow rules with an attached wildcard, such as `Bash(ls*)`, skipping the permission prompt in some cases; a rule that names a variable, such as `Bash(NODE_ENV*)`, now asks

## 概要

2.1.323では、Bashの権限チェックに関する多くの修正が入りました。ワイルドカード付き許可ルールの扱い、`sudo` や `env` などのラッパー経由のdeny/askルール、`rm` の危険な削除確認などが対象です。意図せず確認なしで実行されるケースが減ります。

## 基本的な使い方

`settings.json` のルールを見直します。

```json
{
  "permissions": {
    "allow": [
      "Bash(ls *)",
      "Bash(npm run dev)"
    ]
  }
}
```

`*` を変数の値に入れた `Bash(PORT=* npm run dev)` のようなルールは、起動時に警告が出ます。

## 実践例

### ワイルドカードの書き方を見直す

`Bash(ls*)` のように語尾に直接 `*` を付けるより、`Bash(ls *)` のように区切りを明確にしたルールが安全です。

### 「今後確認しない」の挙動

`.git` や `.claude` など機密性の高いパスへ書き込むコマンドでは、「don't ask again」が提示されなくなりました。また、秘密情報に見えるルールや、gitで追跡される `settings.local.json` に保存されるルールは、そのセッション限りで保存されません。

## 注意点

- 既存のルールで、これまで確認なしに通っていたコマンドが確認を求めるようになる場合があります
- `sudo` の複合フラグや `sandbox.excludedCommands` に関する修正も含まれます
- `--permission-mode auto` が使えない場合は、より許可の広いモードではなくManualモードで起動します
