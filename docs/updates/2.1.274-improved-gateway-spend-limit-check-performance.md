## 原文（日本語訳）
高負荷時のClaude appsゲートウェイの支出上限チェックを改善：これまで4回必要だったデータベースへの往復が1回で済むようになり、負荷の高いゲートウェイでチェックがタイムアウトするケースが減少した。

## 原文（英語）
Improved the Claude apps gateway's spend-limit check under load: it now takes one database round trip instead of four, so fewer checks time out on a busy gateway

## 概要
Claude appsゲートウェイは、組織やユーザーごとの支出上限（スペンドリミット）を超えていないかをリクエストのたびに確認します。これまでこのチェックには4回のデータベース往復が必要で、ゲートウェイが高負荷状態にあるとチェック自体がタイムアウトしてしまうことがありました。今回の改善により、この処理が1回のデータベース往復にまとめられ、高負荷時でもチェックがタイムアウトしにくくなりました。

## 基本的な使い方
この改善は内部処理の最適化であり、ユーザー側の設定変更は不要です。支出上限機能を使っている組織では自動的に恩恵を受けます。

```bash
# 支出上限が設定された組織でのAPIリクエスト例
claude --model claude-sonnet-5
```

## 実践例

### 多数のユーザーが同時にリクエストを送る大規模組織
多くの開発者が同時にClaude Codeを利用する大規模組織のゲートウェイでは、以前は高負荷時に支出上限チェックがタイムアウトし、リクエストが失敗したりエラーになったりすることがありました。改善後はデータベース往復が1回に削減されたことで、同様の負荷下でもチェックが安定して完了しやすくなります。

### 支出上限に近づいている状況でのリクエスト集中
月末など支出上限に近づいたタイミングでリクエストが集中しがちな状況でも、チェック処理自体の負荷が下がったことで、ゲートウェイ全体のレスポンス性能が向上します。

## 注意点
- この改善は支出上限チェックの処理効率に関するものであり、支出上限の設定方法やポリシー自体に変更はありません。
- 依然としてデータベース自体が過負荷状態にある場合は、チェックが遅延・失敗する可能性があります。
