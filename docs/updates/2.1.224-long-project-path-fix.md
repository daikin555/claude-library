## 原文（日本語訳）

200文字を超える長いプロジェクトパスが、共有のサニタイズ済みプレフィックスの下で別のプロジェクトのセッションディレクトリに解決されてしまう問題を修正しました。セッション一覧、リネーム、フォーク、削除、および `/resume` が、プロジェクトをまたいで混在することはなくなりました。

## 原文（英語）

Fixed long (>200 char) project paths resolving to another project's session directory under a shared sanitized prefix; session list, rename, fork, delete and `/resume` no longer cross projects

## 概要

Claude Codeはプロジェクトごとのセッション情報を `~/.claude/projects/<サニタイズされたプロジェクトパス>/` 以下に保存します。プロジェクトパスは `/` を `-` などに置き換える形でサニタイズされてディレクトリ名になりますが、パスが200文字を超えるような非常に深い階層のディレクトリでは、サニタイズ後のプレフィックスが別プロジェクトのものと衝突してしまうケースがありました。この修正により、長いパスを持つプロジェクト同士でも、セッション一覧・リネーム・フォーク・削除・`/resume` の対象が正しく区別されるようになりました。

## 基本的な使い方

セッション管理の操作自体に変更はありません。通常どおり `claude` を起動し、`/resume` でセッション一覧を開くだけです。

```bash
cd /path/to/your/deeply/nested/project
claude
# セッション履歴の一覧を確認
/resume
```

内部的には、プロジェクトパスの長さに関わらず、他のプロジェクトのセッションと取り違えられることなく、常に現在のプロジェクトに紐づくセッションのみが表示されます。

## 実践例

### モノレポの深い階層で作業する場合

大規模なモノレポでは、パッケージやサービスのディレクトリが何階層にもネストし、絶対パスが200文字を超えることがあります。

```bash
cd /home/user/workspace/company-monorepo/services/backend/internal/payments/processing/gateway-integration
claude

# 修正前: パスが長いため、別の深い階層のプロジェクト
# （例: .../gateway-integration-v2/ のような似た階層）
# のセッションが誤って一覧に表示されたり、
# /resume で別プロジェクトのセッションが復元されてしまうことがあった

# 修正後: パスの長さに関わらず、常に正しいプロジェクトの
# セッションだけが一覧・復元の対象になる
/resume
```

### セッションのリネーム・フォーク・削除を行う場合

長いパスのプロジェクトで `/resume` からセッションをリネームしたり、フォークしたり、削除したりする操作も、正しいプロジェクトのセッションだけに適用されます。

```bash
cd /home/user/projects/very/long/path/that/exceeds/two/hundred/characters/example-app
claude
/resume
# セッションをリネーム・フォーク・削除しても、
# サニタイズ後のプレフィックスが同じ別プロジェクトの
# セッションに影響が及ぶことはない
```

### CI環境やクラウドIDEなど、パスが自動生成される環境

CIのチェックアウトパスやクラウド開発環境（Codespaces、Cloud IDEなど）では、ユーザーが意図せず長い絶対パスでプロジェクトを開くことがあります。このようなケースでも、他プロジェクトとのセッション混在を心配せずに `claude` を利用できます。

## 注意点

- この修正はセッションの保存先ディレクトリの解決ロジックに関するものであり、ユーザー側で特別な設定を行う必要はありません
- 修正前に長いパスのプロジェクトで作成・混在してしまったセッションについては、事後的に自動で復元・再割り当てされるわけではない点に注意してください
- プロジェクトパスを可能な限り短く保つことは、可読性の面でも引き続き推奨されます
