## 原文（日本語訳）

`apiKeyHelper` が短命なJWTを返す場合に、アイドル状態後の最初のプロンプトでAPIエラーが表示される問題を修正しました。期限切れのキャッシュ済みトークンは送信前に更新されるようになり、401/403の認証エラーは静かにリトライされるようになりました。

## 原文（英語）

Fixed a visible API error on the first prompt after idle when `apiKeyHelper` returns short-lived JWTs: an expired cached token is now refreshed before sending, and 401/403 auth errors retry quietly

## 概要

`apiKeyHelper` は、APIキーの代わりに外部スクリプトなどを使って動的に認証トークンを取得する仕組みで、短い有効期限のJWTを発行する認証システムと組み合わせて使われることがあります。これまでは、セッションが一定時間アイドル状態になった後に最初のプロンプトを送信すると、キャッシュされたトークンが既に期限切れになっているにもかかわらずそのまま送信されてしまい、APIエラーがユーザーに表示されてしまうことがありました。今回の修正により、送信前にキャッシュされたトークンの期限切れを検知して更新するようになり、さらに万一401/403の認証エラーが発生した場合も、ユーザーに見える形でエラーを出さずに静かにリトライするようになりました。

## 基本的な使い方

`apiKeyHelper` を設定して短命なJWTを使っている場合、特別な操作は不要です。アイドル状態からの復帰後もエラーが表示されず、そのままプロンプトが処理されます。

```json
{
  "apiKeyHelper": "/path/to/get-short-lived-jwt.sh"
}
```

```bash
# しばらく操作せずアイドルになった後、最初のプロンプトを送信
# 修正前: 期限切れトークンによりAPIエラーが表示されることがあった
# 修正後: トークンが自動更新され、エラーなくレスポンスが返る
```

## 実践例

### 短命トークンを発行する社内認証システムとの連携

社内のSSOやトークン発行サーバーと連携し、`apiKeyHelper` で数分〜数十分の有効期限を持つJWTを取得している構成で、離席後に戻って作業を再開してもエラーに遭遇しなくなりました。

### 長時間の離席をはさむ開発ワークフロー

昼休みや会議などで長時間Claude Codeを操作しない時間があった場合でも、再開時の最初のプロンプトでエラー画面に遭遇して困惑する、という体験がなくなります。

### 一時的な認証エラーからの自動回復

トークンの更新タイミングのずれなどにより一時的に401/403が返るケースでも、ユーザーに見える形でエラーとして表示される前に静かにリトライされるため、体感的な信頼性が向上します。

## 注意点

- この修正は `apiKeyHelper` を使い、かつ短命なトークンを発行する構成に特に有効です。固定のAPIキーを使っている場合はそもそも影響を受けにくい問題でした
- リトライは「静かに」行われるため、認証設定自体に根本的な問題がある場合はリトライの裏でエラーが繰り返されている可能性があります。継続的に失敗する場合は `apiKeyHelper` スクリプトやトークン発行元の設定を確認してください
