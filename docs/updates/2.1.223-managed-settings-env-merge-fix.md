## 原文（日本語に翻訳）

managed settingsに関する不具合を修正しました。サーバーから配信された設定によって、マシンローカルの `managed-settings.json` やMDMプロファイルの `env` ブロックが無効化されることがなくなり、管理者が設定した環境変数はキー単位でマージされるようになりました。

## 原文（英語）

Fixed managed settings: server-delivered settings no longer disable the env block of a machine-local `managed-settings.json` or MDM profile; admin env now merges per key

## 概要

Claude Codeのmanaged settings（管理設定）には、claude.ai管理コンソールから配信される「server-managed settings（サーバー管理設定）」と、MDMやOSレベルのポリシー、システム上の `managed-settings.json` ファイルとして配布する「endpoint-managed settings（エンドポイント管理設定）」の2系統があります。この2つは同じ「managed」ティアの中で優先度を持ちますが、原則としてソース同士はマージされず、有効な設定を配信した方が優先されて丸ごと採用される仕組みです。ただし `env` ブロックは例外で、テレメトリ関連の一部変数などを除き、admin側の各ソースを横断してキー単位でマージされる仕様になっています。修正前のバージョンでは、server-managed settingsが何らかの設定を配信すると、マシンローカルの `managed-settings.json` やMDMプロファイルが定義する `env` ブロック全体が無視されてしまうという不具合があり、エンドポイント側で管理者が設定したプロキシ設定などの環境変数が反映されないケースがありました。v2.1.223でこの不具合が修正され、`env` ブロックはドキュメント通りキー単位でマージされるようになりました。具体的には、各環境変数について最も優先度の高いソースが定義していればその値が使われ、上位ソースが未設定のキーについては下位のadmin管理ソースの値が補完されます。

## 基本的な使い方

エンドポイント管理設定（`managed-settings.json`）は、OSごとの決められたパスに配置します。

```bash
# Linux/WSL
/etc/claude-code/managed-settings.json
```

```json
{
  "env": {
    "HTTPS_PROXY": "https://proxy.corp.example.com:8080"
  }
}
```

設定が正しく反映されているかは `claude doctor` や `/status` で確認できます。

```bash
claude doctor
```

```text
/status
```

## 実践例

### server-managed settingsとMDMのenvを併用してプロキシを配布する

社内プロキシ経由でしか `api.anthropic.com` に到達できない組織では、MDMや `managed-settings.json` の `env` にプロキシ変数を設定しておくと、server-managed settingsの取得リクエスト自体にもこの値が反映されます。

```json
{
  "env": {
    "HTTPS_PROXY": "https://proxy.corp.example.com:8080"
  }
}
```

v2.1.223以降では、claude.ai管理コンソール側でserver-managed settingsに別の環境変数（例: テレメトリ設定）を配信していても、このエンドポイント側の `HTTPS_PROXY` は無効化されずキー単位でマージされ、有効なまま残ります。

### server-managed settingsが定義していないキーだけをMDM側で補完する

server-managed settingsが `CLAUDE_CODE_ENABLE_TELEMETRY` のみを配信し、MDMプロファイル側で追加のキーを設定しているケースです。

```json
{
  "env": {
    "CLAUDE_CODE_ENABLE_TELEMETRY": "1"
  }
}
```

```xml
<!-- macOS: com.anthropic.claudecode 管理プレファレンスドメイン -->
<key>env</key>
<dict>
  <key>NODE_EXTRA_CA_CERTS</key>
  <string>/etc/ssl/certs/corp-ca.pem</string>
</dict>
```

この場合、`CLAUDE_CODE_ENABLE_TELEMETRY` はserver-managed settings側の値が優先され、`NODE_EXTRA_CA_CERTS` はサーバー側で未設定のためMDM側の値がそのまま反映されます。

### 設定の反映状況をトラブルシューティングする

意図した環境変数が反映されているか怪しい場合は、`/status` でどのmanagedソースがアクティブか確認し、`claude --debug-file` でデバッグログを取得します。

```bash
claude --debug-file /tmp/claude-debug.log
```

```bash
grep -i "Remote settings" /tmp/claude-debug.log
```

## 注意点

- 本修正はClaude Code v2.1.223以降で有効です。それより前のバージョンでは、server-managed settingsが何かしらの設定を配信すると、エンドポイント管理設定側の `env` ブロック全体が無視される点に注意してください。
- `env` のキー単位マージは例外的な扱いであり、`env` 以外の大半のキーについては「有効な設定を配信した最初のソースが丸ごと採用され、他のソースはマージされない」という原則は変わりません。
- OTELエクスポーター関連の変数群（`OTEL_EXPORTER_OTLP_*` など）や、`apiKeyHelper`・`otelHeadersHelper` のような認証情報系キーとペアになるルーティング変数は、キー単位マージの対象外として「まとまり（ユニット）」単位で最優先ソースの値が採用されます。
- サーバー配信のキャッシュされた `env` ブロックのうち、プロキシ・TLS設定や認証情報など一部のカテゴリは、セッション開始時にサーバーへの再フェッチが確認されるまで「保留（withheld）」されます。エンドポイント管理設定はこの保留の対象外です。
- 反映状況を確認するには `/status` や `claude doctor` を利用し、不正なエントリがある場合は警告とともにストリップ（無視）される点も把握しておくとよいでしょう。
