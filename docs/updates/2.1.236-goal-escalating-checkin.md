## 原文（日本語訳）

`/goal`: ゴールが長時間のバックグラウンド作業の裏で止まったままアイドル状態になっているセッションは、ユーザーの復帰を待つのではなく、30分後（その後1時間後、2時間後）に自動的に状況を確認しにいくようになりました。

## 原文（英語）

`/goal`: an idle session whose goal is parked behind long-running background work now checks in automatically after 30 minutes (then 1h, 2h) instead of waiting for you to return

## 概要

2.1.234で導入された「バックグラウンドタスクが30分以上続くとClaudeが状況を確認する」機能をさらに発展させたものです。従来は最初の30分でチェックインした後、以降も一律30分おきに確認が続く仕様でしたが、今回の変更では、ユーザーが完全に離席していて（アイドル状態で）ゴールがバックグラウンド作業の裏に「置き去り」になっているセッションに対して、30分・1時間・2時間と間隔を段階的に広げながらチェックインするようになりました。これにより、ユーザーがすぐ戻ってこない見込みの高い状況では確認頻度を落としつつも、作業が完全に放置されることを防ぎます。

## 基本的な使い方

特別な操作は不要です。`/goal` でゴールを設定した状態でバックグラウンドタスクが動いており、かつユーザー側の操作がしばらくない（アイドル）場合、Claudeは30分後に最初のチェックインを行い、その後は1時間後、2時間後と間隔を空けながら自動的に状況確認を続けます。

```
/goal 全テストスイートが通り、ビルド成果物が生成される
```

## 実践例

### 長時間のCIビルドを離席中に見守らせる

```
/goal リリースビルドが完了し、成果物がdist/に出力される
```

ビルドに数時間かかる場合、最初のチェックインは30分後に行われます。その時点でまだユーザーが操作を再開していなければ、次のチェックインは1時間後、その次は2時間後というように間隔が広がっていき、無駄なチェックインでリソースを消費しすぎないようにしつつ、進捗の停滞や失敗を早期に検知できます。

### 短時間で戻ってくる場合との違い

ユーザーがすぐに別の指示を出したりセッションを操作したりする場合は、セッションは「アイドル」とは判定されないため、この段階的チェックインの対象にはなりません。あくまで「ゴールがバックグラウンド作業の裏に置き去りにされ、かつユーザーも操作していない」という条件がそろったときに適用される挙動です。

### チェックイン頻度を制御する

2.1.234で導入された `CLAUDE_CODE_GOAL_CHECKIN_MINUTES` 環境変数は引き続き有効です。`0` に設定すればチェックイン自体を無効化でき、従来どおり無期限に待つ挙動に戻せます。

```
export CLAUDE_CODE_GOAL_CHECKIN_MINUTES=0
```

## 注意点

- この段階的チェックイン（30分→1時間→2時間）は、セッションがアイドル状態でゴールが長時間バックグラウンド作業の裏にある場合に適用されます
- チェックイン自体を無効にしたい場合は、引き続き `CLAUDE_CODE_GOAL_CHECKIN_MINUTES=0` を設定します
- 2.1.234で導入された「30分ごとの一律チェックイン」の基本動作を置き換えるのではなく、アイドル時の間隔を賢く広げる改良である点に注意してください
