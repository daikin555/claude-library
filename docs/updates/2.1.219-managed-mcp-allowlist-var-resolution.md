## 原文（日本語に翻訳）

managed MCP allowlist/denylistの `${VAR}` エントリの解決元を、settings-file（設定ファイル）のenvではなく、起動時の環境変数とmanaged-settingsのenvから解決するように変更した。

## 原文（英語）

Changed managed MCP allowlist/denylist `${VAR}` entries to resolve from the startup environment and managed-settings env instead of settings-file env

## 概要

Claude Codeの組織向けmanaged settingsには、利用を許可・禁止するMCPサーバーを制御するallowlist/denylistの仕組みがあり、そのエントリ内で `${VAR}` のようなプレースホルダーを使って値を動的に埋め込むことができます。従来この `${VAR}` は、settings.jsonファイル自体に定義された `env` セクションの値からも解決されていましたが、これはユーザーがローカルのsettings.jsonを書き換えることで実効値に影響を与えられる余地を意味していました。2.1.219では、この解決元が「Claude Code起動時点のシェル環境変数」と「managed-settingsファイルの `env` セクション」に限定され、通常のプロジェクト/ユーザー設定ファイルのenvは参照されなくなりました。

## 基本的な使い方

管理者はmanaged-settings.json（組織のIT/セキュリティ部門が配布し、エンドユーザーが変更できない設定ファイル）の中で、allowlist/denylistのエントリに `${VAR}` 形式のプレースホルダーを記述します。

```json
{
  "mcpServers": {
    "allowlist": [
      "internal-search@${MCP_REGISTRY_HOST}"
    ],
    "denylist": [
      "*@${UNTRUSTED_REGISTRY_HOST}"
    ]
  },
  "env": {
    "MCP_REGISTRY_HOST": "mcp.internal.example.com"
  }
}
```

この状態でClaude Codeを起動すると、`${MCP_REGISTRY_HOST}` はmanaged-settings.json内の `env.MCP_REGISTRY_HOST` の値（`mcp.internal.example.com`）に解決されます。ユーザー側のプロジェクトやホームディレクトリの `settings.json` に同名の `env.MCP_REGISTRY_HOST` を定義しても、allowlist/denylistの解決には一切使用されません。

## 実践例

### 起動時のシェル環境変数を使ったマルチ環境対応

CI/CDやデプロイスクリプトから環境ごとに異なるレジストリホストを注入したい場合、managed-settings.json側では変数名だけを参照させ、実値はOS環境変数として渡します。

```json
{
  "mcpServers": {
    "allowlist": ["*@${MCP_REGISTRY_HOST}"]
  }
}
```

```bash
# 本番環境用の起動スクリプト
export MCP_REGISTRY_HOST="mcp.prod.example.com"
claude

# 開発環境用の起動スクリプト
export MCP_REGISTRY_HOST="mcp.dev.example.com"
claude
```

2.1.219以降は、この `MCP_REGISTRY_HOST` はClaude Code起動時点のシェル環境から読み取られます。ユーザーが後からプロジェクトの `.claude/settings.json` に `env.MCP_REGISTRY_HOST` を追記しても、allowlist/denylistの判定には影響しません。

### managed-settings.jsonのenvで組織全体のポリシーを固定する

複数チームで同じmanaged-settings.jsonを配布し、レジストリのホスト名をmanaged-settings側の `env` に固定することで、ユーザー環境の差異に関係なく常に同じ値が使われるようにできます。

```json
{
  "mcpServers": {
    "denylist": ["*@${EXTERNAL_MCP_HOST}"]
  },
  "env": {
    "EXTERNAL_MCP_HOST": "public-registry.example.com"
  }
}
```

管理者がmanaged-settings.jsonを配布した端末では、たとえユーザーがOSの環境変数やローカルsettings.jsonで `EXTERNAL_MCP_HOST` を別の値に上書きしようとしても、managed-settings.json内のenv定義が優先して解決される（settings-file envは解決対象外になった）ため、denylistの実効性が保たれます。

### 移行時の設定チェック

これまでプロジェクト/ユーザーのsettings.jsonの `env` に頼ってallowlist/denylistの `${VAR}` を解決していた構成では、2.1.219へのアップグレード後にプレースホルダーが解決できず、想定していたMCPサーバーが許可・拒否されなくなる可能性があります。移行時は以下を確認してください。

```bash
# 現在有効なmanaged-settingsの内容を確認
claude config get --managed

# allowlist/denylistで使われている変数名を洗い出し、
# managed-settings.jsonのenvまたは起動シェルのexportに移設する
grep -R '\$\{' /path/to/managed-settings.json
```

## 注意点

- この変更はセキュリティ強化を目的としており、ユーザーが変更可能な設定ファイル（プロジェクト/ユーザーのsettings.json）の `env` は、allowlist/denylist内の `${VAR}` 解決には一切使われなくなります。
- allowlist/denylistで使う変数は、（1）managed-settings.jsonの `env` セクション、または（2）Claude Code起動時点ですでにエクスポートされているシェル環境変数、のいずれかで定義する必要があります。
- シェル起動後に対話的に `export` した値や、Claude Code起動後に変更した環境変数は反映されません（「起動時」の環境が対象のため）。
- 通常のMCPサーバー定義（`.mcp.json` のserver設定など）における環境変数展開の挙動とは別物であり、本変更はあくまでallowlist/denylistの判定ロジックに限定されます。
- アップグレード後は、意図したMCPサーバーが引き続き許可/拒否されているか、`claude mcp list` 等で必ず動作確認することを推奨します。
