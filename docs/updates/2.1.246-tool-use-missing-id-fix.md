## 原文（日本語訳）

サードパーティのAnthropic互換エンドポイント（`ANTHROPIC_BASE_URL`）が `id` を持たない `tool_use` ブロックをストリーミングした場合、最初のツール呼び出しでUIがレンダーエラーで停止してしまう不具合を修正しました。

## 原文（英語）

Fixed the UI stopping with a render error on the first tool call when a third-party Anthropic-compatible endpoint (`ANTHROPIC_BASE_URL`) streams a `tool_use` block without an `id`

## 概要

Claude Codeは `ANTHROPIC_BASE_URL` 環境変数を設定することで、Anthropic API互換のサードパーティエンドポイントに接続できます。しかし、一部の互換エンドポイントがAnthropic APIの仕様と異なり `id` フィールドを持たない `tool_use` ブロックをストリーミングで返す場合があり、これを受け取った際に最初のツール呼び出しでUI全体がレンダーエラーとなり動作が停止してしまう不具合がありました。今回の修正により、`id` のない `tool_use` ブロックを受け取ってもUIがクラッシュせず、処理を継続できるようになりました。

## 基本的な使い方

`ANTHROPIC_BASE_URL` を設定してサードパーティの互換エンドポイントを利用する場合の手順自体は変わりません。

```bash
export ANTHROPIC_BASE_URL="https://your-compatible-endpoint.example.com"
claude
```

修正後は、接続先のエンドポイントが仕様通りに `id` を含まない `tool_use` ブロックを返してきても、UIがエラーで停止することなくツール呼び出しの処理を続けられます。

## 実践例

### 自前でホストしたAnthropic互換プロキシを利用する

社内で構築したプロキシサーバーやゲートウェイ経由でClaude Codeを利用している場合、実装の細部でAPIレスポンスの形式に差異があっても、UI全体がクラッシュするリスクが減ります。

### サードパーティのモデルゲートウェイ経由での利用

複数のLLMプロバイダーを統一的に扱うゲートウェイ製品を介して接続する構成でも、レスポンス形式の細かな非互換性によって作業が中断されにくくなります。

### 互換エンドポイントの開発・デバッグ中

自作のAnthropic互換エンドポイントを開発している最中に、まだ `id` の付与が未実装の段階でも、Claude Code側のUIが落ちずに動作を確認できます。

## 注意点

- これはUIのクラッシュを防ぐための耐性向上の修正であり、`id` を持たない `tool_use` ブロックを送信してくるエンドポイント自体の仕様が推奨されるわけではありません。可能であればエンドポイント側でAnthropic APIの仕様に準拠した `id` を付与することが望まれます
- 公式のAnthropic APIを直接利用している場合はこの問題の影響を受けません
