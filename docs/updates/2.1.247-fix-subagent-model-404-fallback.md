## 原文（日本語訳）

サブエージェントが最初のモデル呼び出しで404エラーを受け取った場合に処理が停止してしまう不具合を修正しました。現在ではセッションのフォールバックモデルチェーンを利用するようになり、親エージェントに返されるエラーにはエラータイプ、ステータス、リクエストID、モデル名が含まれるようになりました。

## 原文（英語）

Fixed sub-agents dying on a first-call model 404: they now use the session's fallback model chain, and the error returned to the parent includes the error type, status, request id, and model

## 概要

サブエージェント（Agentツールで起動される子エージェント）が最初のモデル呼び出し時に404エラー（指定モデルが見つからない等）を受け取ると、これまではそのままサブエージェントが停止してしまい、親エージェント側にはエラーの詳細が十分に伝わらないことがありました。今回の修正により、サブエージェントもセッションに設定されたフォールバックモデルチェーンを利用するようになり、最初のモデルが使えない場合でも自動的に次のモデルで再試行されます。また、それでも失敗した場合に親エージェントへ返されるエラー情報が拡充され、エラータイプ・HTTPステータス・リクエストID・使用しようとしたモデル名が含まれるようになったため、原因調査がしやすくなりました。

## 基本的な使い方

ユーザー側で明示的な操作は不要です。フォールバックモデルチェーンは通常のセッション設定（`settings.json` の `model` 関連設定など）に基づいて動作します。

```json
{
  "model": "claude-opus-4-6"
}
```

サブエージェントが起動する際、指定モデルの呼び出しが404で失敗しても、フォールバックチェーンの次のモデルで自動的に再試行されるようになります。

## 実践例

### 一時的にモデルIDが利用できない環境でのサブエージェント実行

新しいモデルへの切り替え直後や、特定のモデルが一時的にリージョン等で利用不可な場合でも、サブエージェントが即座に停止せず、フォールバックチェーンの別モデルで処理を継続できます。

### 親エージェントでのエラー原因調査

サブエージェントが最終的に失敗した場合でも、親エージェントに渡されるエラーにエラータイプ・ステータスコード・リクエストID・モデル名が含まれるため、どのモデル・どのリクエストが原因だったかを特定しやすくなります。

### Agentツールを多用するワークフローの安定性向上

複数のサブエージェントを並行・連続して起動するようなワークフローで、一部のモデル呼び出しが不安定な場合でも、全体のタスクが途中で完全に停止するリスクが減ります。

## 注意点

- フォールバックモデルチェーンが設定されていない場合、フォールバック先が存在しないため、最終的にエラーとなる可能性があります
- フォールバックにより実際に使用されるモデルが意図したものと異なる場合があるため、エラー情報に含まれるモデル名を確認することが推奨されます
- この修正はサブエージェントの初回呼び出し時の404エラーに関するものであり、他の種類のエラー（レート制限など）の扱いを変更するものではありません
