## 原文（日本語訳）

「APIが空または不正な形式のレスポンスを返しました」というエラーメッセージを改善し、実際に返ってきた内容（コンテンツタイプ、ボディの種類、サイズ、リクエストID）と、元のストリーミングリクエストが失敗した理由を表示するようにしました。

## 原文（英語）

Improved the "API returned an empty or malformed response" error to say what came back (content type, body kind, size, request ID) and why the original streaming request failed

## 概要

従来、APIから空または不正な形式のレスポンスが返ってきた場合、Claude Codeは「API returned an empty or malformed response」という汎用的なメッセージしか表示せず、原因の切り分けが困難でした。今回の改善により、実際に返ってきたレスポンスのコンテンツタイプ、ボディの種類、サイズ、リクエストIDに加え、そもそもストリーミングリクエストがなぜ失敗したのかという根本原因も表示されるようになり、トラブルシューティングが格段にしやすくなりました。

## 基本的な使い方

この変更はエラー発生時の表示内容の改善であり、ユーザー側で何か操作を行う必要はありません。エラーが発生した際、以前より詳細な診断情報が自動的にターミナルに表示されます。

改善前のイメージ:
```
Error: API returned an empty or malformed response
```

改善後のイメージ:
```
Error: API returned an empty or malformed response
  content-type: text/html
  body kind: empty
  size: 0 bytes
  request id: req_01AbCdEfGhIjKlMnOpQrStUv
  reason: streaming request failed with a network timeout before any chunk was received
```

## 実践例

### ネットワーク不調時の原因切り分け

社内ネットワークやプロキシの不調でAPIレスポンスが途中で切れた場合、以前は原因不明のエラーとして扱われていましたが、改善後はストリーミング接続がどの段階で失敗したかがメッセージに含まれるため、ネットワーク側の問題かクライアント側の問題かを即座に判断できます。

### サポート問い合わせ時の情報提供

Anthropicサポートやコミュニティに問題を報告する際、表示されるリクエストID（`request id`）をそのまま添えることで、サーバー側のログと突き合わせた調査を依頼しやすくなります。

```
サポートへの報告例:
「2.1.234でストリーミングリクエストが失敗しました。
request id: req_01AbCdEfGhIjKlMnOpQrStUv
content-type: application/json, body kind: malformed, size: 12 bytes」
```

### プロキシ・ゲートウェイ経由利用時の切り分け

社内プロキシやAPIゲートウェイを経由して利用している環境で、レスポンスがHTML（エラーページ）として返ってきているケースなどは、`content-type: text/html` という情報から、APIエンドポイントの設定ミスやゲートウェイ側のブロックにすぐ気づけます。

## 注意点

- あくまでエラーメッセージの情報量が増えただけで、エラー自体の発生条件が変わるわけではありません
- 表示される項目（コンテンツタイプ、ボディの種類、サイズ、リクエストID、失敗理由）は状況によって取得できない場合があります
- リクエストIDが取得できた場合は、サポートへの問い合わせ時に共有すると調査がスムーズです
