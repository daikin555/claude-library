## 原文（日本語に翻訳）

`sandbox.filesystem.denyWrite` が作業ディレクトリを含む設定になっている場合に、Linux上でサンドボックス化されたコマンドが起動できなくなる不具合を修正しました。

## 原文（英語）

Fixed sandboxed commands failing to start on Linux when `sandbox.filesystem.denyWrite` covers the working directory

## 概要

Claude CodeのBashサンドボックス機能は、コマンドが触れてよいファイルやディレクトリをOSレベルで制限する仕組みです。`sandbox.filesystem.denyWrite` を使って、書き込みを禁止したいパス（`.git/hooks` や設定ファイルなど）を指定できますが、そのパスが現在の作業ディレクトリ自体、あるいは作業ディレクトリを包含するパスと重なっている場合、Linux環境ではサンドボックスの初期化ロジックが矛盾した状態になり、サンドボックス化されたコマンドがそもそも起動できなくなる不具合がありました。今回の修正により、作業ディレクトリと `denyWrite` の対象が重なるケースでも正しくコマンドが起動するようになりました。

## 基本的な使い方

サンドボックスの状態やモード、`denyWrite` の設定は `/sandbox` コマンドから確認・変更できます。

```text
/sandbox
```

`settings.json` で直接 `denyWrite` を指定する場合は、以下のように記述します。

```json
{
  "sandbox": {
    "filesystem": {
      "denyWrite": ["~/.claude/settings.json", "/project/.claude/hooks"]
    }
  }
}
```

修正後は、作業ディレクトリ配下のパスを `denyWrite` に含めていても、Linux上でサンドボックス化されたBashコマンドが正常に起動することを確認できます。

## 実践例

### 作業ディレクトリ配下の機密ファイルだけ書き込み禁止にする

リポジトリのルートが作業ディレクトリの場合、その中の特定ディレクトリを書き込み禁止にしたいケースがあります。修正前はこの設定が原因でLinux上のサンドボックスコマンドが起動しないことがありましたが、修正後は問題なく動作します。

```json
{
  "sandbox": {
    "filesystem": {
      "denyWrite": ["/project/secrets", "/project/.env"]
    }
  }
}
```

```bash
# サンドボックス内でビルドコマンドを実行しても、
# secretsディレクトリへの書き込みだけが拒否される
npm run build
```

### CI環境で作業ディレクトリ全体を対象にする厳格な設定

CIパイプラインなどで、成果物ディレクトリ以外への書き込みを一切許可しない厳格な運用をしたい場合、作業ディレクトリ自体を `denyWrite` に含める設定を組むことがあります。

```json
{
  "sandbox": {
    "filesystem": {
      "denyWrite": ["/workspace"],
      "allowWrite": ["/workspace/dist"]
    }
  }
}
```

### 更新後にサンドボックスの動作確認を行う

`sandbox.filesystem.denyWrite` を作業ディレクトリと重なる形で設定しているプロジェクトでは、アップデート後に `/sandbox` パネルから状態を確認し、コマンドが正常に起動するかを念のためチェックすることをおすすめします。

```text
/sandbox
```

## 注意点

- 本修正はLinux（およびWSL2）環境のサンドボックスに関するものです。macOSのSeatbelt実装には直接関係しない可能性があります。
- `denyWrite` はあくまで書き込みを禁止する設定であり、読み取りを制限したい場合は `denyRead` を別途設定する必要があります。
- サンドボックスに必要な依存パッケージ（seccompフィルタなど）が未導入の場合、`/sandbox` のDependenciesタブで案内が表示されます。
