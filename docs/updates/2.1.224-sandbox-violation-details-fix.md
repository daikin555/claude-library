## 原文（日本語訳）

sandboxの違反詳細がBashツールの結果に一切表示されない問題を修正しました。Claudeは現在、どのファイルまたはネットワークアクセスが拒否されたか、またその理由を確認できるようになりました。

## 原文（英語）

Fixed sandbox violation details never appearing in Bash tool results; Claude now sees which file or network access was denied and why

## 概要

sandbox化されたBashツールでコマンドがファイルシステムやネットワークのアクセス制限に違反すると、そのコマンドはブロックされます。しかし従来は、なぜ・どのアクセスがブロックされたのかという詳細情報がBashツールの実行結果に反映されず、Claudeにはコマンドが失敗したことしか伝わっていませんでした。この修正により、拒否されたファイルパスやネットワーク先、拒否理由がBashツールの結果に含まれるようになり、Claudeが原因を理解した上で適切な代替手段を選べるようになりました。

## 基本的な使い方

sandboxを有効化した状態で、通常どおりBashコマンドを実行するだけです。特別な操作は不要です。

```json
{
  "sandbox": {
    "enabled": true,
    "filesystem": {
      "denyRead": ["~/.aws/"]
    }
  }
}
```

sandboxポリシーに違反するコマンドを実行すると、Bashツールの結果にどのアクセスが・なぜ拒否されたかが含まれるようになりました。

## 実践例

### 拒否されたファイルアクセスの原因をClaudeが理解できる

```bash
cat ~/.aws/credentials
```

```text
# 修正前:
# Bashツールの結果には単に「コマンドが失敗した」
# （終了コードやエラーのみ）としか表示されず、
# Claudeはsandboxの制限によるものだと認識できず、
# 見当違いのデバッグ（権限変更やパス変更の提案など）を
# 繰り返すことがあった

# 修正後:
# Bashツールの結果に以下のような違反詳細が含まれる
# Sandbox violation: read access to "~/.aws/credentials" was denied
# by filesystem.denyRead rule "~/.aws/"
# → Claudeはアクセスが意図的にブロックされたものだと理解し、
#   ユーザーに許可を求める、または別の方法を提案できる
```

### ネットワークアクセスが拒否された場合の切り分け

sandboxのネットワークプロキシで許可されていないドメインへのアクセスが発生した場合も同様です。

```bash
curl https://internal-api.example.com/data
```

```text
# 修正前: 単なる接続エラーとしか見えず、
# Claudeはネットワーク自体の不調と誤認することがあった

# 修正後: Bashツールの結果に
# Sandbox violation: network access to "internal-api.example.com"
# was denied (domain not in allowlist)
# のような詳細が含まれ、Claudeはドメイン許可が必要だと理解できる
```

### 複雑なCI/ビルドスクリプトでのトラブルシューティング

複数のコマンドを含むビルドスクリプトの途中でsandbox違反が発生した場合、詳細情報があることでClaudeがスクリプトのどの部分・どのアクセスが原因かを特定しやすくなり、無駄な試行錯誤を減らせます。

## 注意点

- この修正はsandboxを有効化している場合にのみ関係します
- 違反詳細が表示されるようになったことで、Claudeがアクセス許可の追加（`allowRead`/`allowWrite`やネットワークドメインの許可）をユーザーに提案する場面が増える可能性があります
- 機密性の高いパスやドメインを意図的に拒否している場合、その拒否理由の文言自体にはパスやドメイン名が含まれるため、ログの取り扱いには通常のsandbox設定と同様の注意を払ってください
