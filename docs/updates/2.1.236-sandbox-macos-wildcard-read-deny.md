## 原文（日本語訳）

サンドボックス機能について、macOSにおいて `**/.env` のようなワイルドカードによる読み取り拒否ルールが、許可された読み取り領域の内側でも優先されるようになりました。一致したディレクトリ配下の内容もまとめて対象となり、拒否対象のファイルをリネームすることで拒否ルールをすり抜けることもできなくなりました。

## 原文（英語）

Sandbox: on macOS, wildcard read-deny rules (e.g. `**/.env`) now take precedence inside allowed read regions, cover matched directories' contents, and can't be bypassed by renaming the denied file

## 概要

Claude Codeのサンドボックス機能では、`sandbox.filesystem.denyRead` で特定のファイルやディレクトリへの読み取りを拒否し、`allowRead` で拒否領域の一部を再度許可する、といった設定を組み合わせて使います。今回の修正はmacOS（Seatbelt）上でのワイルドカードによる拒否ルールの適用を強化するもので、`**/.env` のようなパターンが、より広い許可領域の内側にあっても確実に優先されるようになりました。また、パターンに一致したディレクトリの中身もまとめて拒否対象になり、ファイル名を変更することで拒否ルールを回避することもできなくなりました。

## 基本的な使い方

`.claude/settings.json` などでワイルドカードの拒否ルールを設定します。

```json
{
  "sandbox": {
    "filesystem": {
      "allowRead": ["~/projects"],
      "denyRead": ["**/.env"]
    }
  }
}
```

この設定では `~/projects` 配下は基本的に読み取り可能ですが、その中に含まれる `.env` ファイル（サブディレクトリのものも含む）は今回の修正により確実にブロックされます。

## 実践例

### プロジェクト全体を読み取り許可しつつ.envだけ確実に守る

リポジトリ全体をサンドボックスの読み取り許可対象にしつつ、環境変数ファイルだけは秘密情報として守りたいケースは多くあります。`allowRead` で広くプロジェクトを許可し、`denyRead` に `**/.env` を指定しておけば、修正前は許可領域内で拒否ルールが期待通り効かないケースがありましたが、修正後は確実にブロックされます。

### モノレポの各パッケージ配下の環境ファイルもまとめて保護

`packages/*/.env` のように複数のディレクトリに散らばった環境ファイルも、ワイルドカードパターン `**/.env` で一括して拒否対象にできます。パターンに一致したディレクトリの中身もカバーされるため、サブディレクトリを掘って追加された設定ファイル群も含めて保護されます。

### ファイル名変更によるすり抜けを防ぐ

以前は `.env` を `.env.local.bak` のような別名にリネームすることで拒否ルールを回避できてしまう余地がありましたが、今回の修正でそうした回避策も塞がれています。

## 注意点

- この修正はmacOS（Seatbelt）上でのサンドボックスのファイルシステム層に関するものです。Linux/WSL2では別の実装で拒否ルールが適用されます
- サンドボックスの `denyRead`/`allowRead` は、`Read`/`Edit` ツールに対するパーミッションルールとは別の仕組みです。両方を併用することでより強固に保護できます
- 拒否ルールは常に許可ルールより優先されます。狭い許可では拒否領域を再開放できません
- 認証情報ファイルのような機密ファイルをより体系的に守りたい場合は `sandbox.credentials.files` の利用も検討してください
