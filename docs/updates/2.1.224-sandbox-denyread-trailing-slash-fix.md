## 原文（日本語訳）

末尾にスラッシュを付けて記述されたsandboxのファイルシステムdenyエントリ（例: `denyRead: "~/.aws/"`）が、LinuxおよびmacOSで気付かれないままバイパスされてしまう問題を修正しました。

## 原文（英語）

Fixed sandbox filesystem deny entries written with a trailing slash (e.g. `denyRead: "~/.aws/"`) being silently bypassable on Linux and macOS

## 概要

Claude Codeのsandbox機能では、`settings.json` の `sandbox.filesystem.denyRead` / `denyWrite` に指定したパスへのアクセスを拒否できます。しかし、パスの末尾にスラッシュ（`/`）を付けて記述した場合（例: `"~/.aws/"`）、LinuxとmacOSではそのパターンが正しく適用されず、本来拒否されるべきディレクトリへの読み取りアクセスが気付かれないまま許可されてしまう不具合がありました。この修正により、末尾スラッシュの有無にかかわらずdenyエントリが確実に適用されるようになりました。

## 基本的な使い方

`sandbox.filesystem.denyRead` はこれまでどおり `settings.json` で設定します。

```json
{
  "sandbox": {
    "enabled": true,
    "filesystem": {
      "denyRead": ["~/.aws/", "~/.ssh/", "~/.config/gcloud/"]
    }
  }
}
```

末尾にスラッシュを付けても付けなくても、指定したディレクトリ配下への読み取りが確実にブロックされます。

## 実践例

### クラウド認証情報ディレクトリを保護する場合

AWS、GCP、Azureなどのクレデンシャルディレクトリを末尾スラッシュ付きで指定していたケースです。

```json
{
  "sandbox": {
    "filesystem": {
      "denyRead": ["~/.aws/", "~/.gcloud/", "~/.azure/"]
    }
  }
}
```

```bash
# 修正前: 末尾スラッシュが付いているため、
# Linux/macOS上ではdenyRead設定が正しく機能せず、
# sandbox化されたBashツールから
# cat ~/.aws/credentials
# が読めてしまうことがあった

# 修正後: 末尾スラッシュの有無に関わらず正しく拒否される
cat ~/.aws/credentials
# => Permission denied by sandbox policy
```

### SSH鍵ディレクトリを保護する場合

`~/.ssh/` のような一般的な書き方（末尾スラッシュあり）で秘密鍵を保護しているプロジェクトです。

```json
{
  "sandbox": {
    "filesystem": {
      "denyRead": ["~/.ssh/"]
    }
  }
}
```

修正前は、この設定がLinux/macOSで意図通りに機能せず、`~/.ssh/id_rsa` などの秘密鍵がsandbox化されたコマンドから読み取れてしまう可能性がありました。修正後は、末尾スラッシュを付けた書き方でも確実に拒否されます。

### 既存の設定ファイルを見直す場合

チームで共有している `.claude/settings.json` に末尾スラッシュ付きのdenyエントリがないか確認しておくと安心です。

```bash
grep -n "denyRead\|denyWrite" .claude/settings.json
```

今回の修正はClaude Code側の挙動修正であり、末尾スラッシュを外すような設定変更は不要ですが、念のため意図した通りにブロックされているかを確認しておくとよいでしょう。

## 注意点

- この問題はLinuxとmacOSに影響するものであり、末尾スラッシュを付けたdenyエントリを使っていた場合、意図した保護が効いていなかった可能性があります
- 機密情報を扱うディレクトリ（`~/.aws/`、`~/.ssh/`、`~/.config/gcloud/` など）を `denyRead`/`denyWrite` で保護している場合は、アップデート後に改めて動作を確認することを推奨します
- `sandbox.credentials` を使うと、既知のクレデンシャルファイルの読み取りや秘密情報を含む環境変数のunsetをまとめて行うこともできます
