## 原文（日本語訳）

中継される権限プレビューにおける認証情報マスキングが、コマンド・パス・送信先を承認者から隠してしまうことがないよう修正しました。また、フル強度のリダクション（編集）を行う際、サイズの大きい秘密鍵ブロックが正しくリダクションされるようになりました。

## 原文（英語）

Fixed: credential masking on relayed permission previews can no longer hide commands, paths, or destinations from the approver; oversized private-key blocks now redact under full-strength redaction

## 概要

Channels経由で権限プロンプトを中継する際、Claude Codeはプレビュー内容に含まれるAPIキーやトークンなどの認証情報を自動的にマスキング（伏せ字化）し、チャンネルの向こう側（Telegramなど）に機微な情報が漏れないようにしています。今回の修正では2つの問題を解消しました。1つ目は、このマスキング処理が過剰に働き、承認者が判断のために本来見るべきコマンド本体・ファイルパス・送信先（ホスト名など）まで隠してしまうことがあった点です。2つ目は、フル強度のリダクションを行う設定下で、サイズの大きい秘密鍵ブロック（PEM形式の鍵など）が正しくリダクションされず、そのまま漏れる可能性があった点です。

## 基本的な使い方

権限プレビューのマスキング自体は自動で行われ、ユーザー側で明示的に操作する項目はありません。Channels経由で権限プロンプトを承認する際、コマンドやファイルパスなどの判断に必要な情報は表示されつつ、認証情報のような機微な値だけが伏せ字になります。

```
Claude> curl -H "Authorization: Bearer sk-***MASKED***" https://api.example.com/deploy を実行しようとしています
[承認 / 却下]
```

## 実践例

### コマンドの実行内容を正しく確認できるようになった

デプロイスクリプトの実行など、コマンド本体の内容が承認判断に重要なケースです。

```
# 修正前: マスキングが過剰に働き、コマンドの一部やパス、
#          送信先ホスト名まで伏せ字になってしまい、
#          何を承認しているのか判断できないことがあった
# 修正後: 認証情報（トークンやキー）のみが伏せ字になり、
#          コマンド・パス・送信先は正しく表示される
```

### 大きな秘密鍵ブロックを含む出力をリダクションする場合

環境変数の出力やファイル内容の表示に、複数行にわたるPEM形式の秘密鍵が含まれるケースです。

```
-----BEGIN PRIVATE KEY-----
MIIEvQIBADANBgkqhkiG9w0BAQEFAASCBKcwggSjAgEAAoIBAQC7Vx...
（数十行にわたる鍵データ）
-----END PRIVATE KEY-----
```

```
# 修正前: フル強度のリダクション設定でも、サイズが大きい鍵ブロックは
#          正しくマスキングされずそのまま中継されることがあった
# 修正後: サイズの大きい秘密鍵ブロックも確実にリダクションされる
```

### チャンネル経由でリモート承認を行う運用

Telegramなどのチャンネルを使い、外出先からデプロイ操作を承認する運用をしているチームでは、この修正により「何を承認しているか正しく確認できる」「秘密鍵などの機微情報は確実に隠される」という両方の安全性が向上します。

## 注意点

- この修正は権限プレビューの中継（Channels経由の権限リレー）を利用している場合に関係します
- マスキングは自動処理ですが、機微情報を含む可能性のある出力を承認する際は、表示内容を注意深く確認することが引き続き推奨されます
- 「フル強度のリダクション」は設定によって強度が異なる場合があるため、組織のセキュリティ要件に応じた設定を確認してください
- 本機能はリサーチプレビュー段階のChannels機能に関するものであり、今後仕様が変更される可能性があります
