## 原文（日本語訳）

ターン間でセッションのコンテナが再起動し、バックグラウンドのエージェント・シェル・モニターがまだ動作中だった場合に、クラウドセッションが応答しなくなる問題を修正しました。再開したセッションは、失われた作業内容を報告するようになりました。

## 原文（英語）

Fixed cloud sessions going silent when the session's container restarts between turns while a background agent, shell, or monitor is still running — the resumed session now reports the lost work

## 概要

クラウドセッションはコンテナ環境上で実行されており、バックグラウンドで動作しているサブエージェントやシェルコマンド、モニタープロセスを保持したまま次のターンに進むことがあります。しかし、ターンの間にコンテナが再起動すると、これらのバックグラウンド処理は失われてしまい、これまでは何の説明もなくセッションが応答しなくなる（サイレントになる）ことがありました。今回の修正で、コンテナ再起動によってバックグラウンド作業が失われた場合、セッション再開時にその旨がユーザーに報告されるようになりました。

## 基本的な使い方

クラウドセッションでバックグラウンドタスク（サブエージェントの実行、長時間のシェルコマンド、ファイル監視など）を動かしている状態で、コンテナの再起動が発生した場合、次にセッションが応答する際に「バックグラウンドで実行していた作業が失われました」といった内容が報告されます。

## 実践例

### 長時間のバックグラウンドエージェントを走らせている場合

複雑な調査や実装をバックグラウンドエージェントに任せている際にコンテナが再起動すると、これまでは結果を待っているのに何も応答が返らず原因が分かりませんでした。修正後は再開時に何が失われたかが明示されるため、タスクを再実行するなどの対処判断がしやすくなります。

### バックグラウンドシェルコマンドを利用している場合

ビルドやテストなどのバックグラウンドシェルコマンドの完了を待っている際にコンテナ再起動が起きた場合も、コマンドが失われたことが報告され、再度コマンドを実行し直す必要があることが分かります。

### ファイル監視（モニター）を使ったワークフロー

継続的にログや出力を監視するモニタープロセスを利用しているワークフローでも、再起動によって監視が途切れたことが分かるようになり、監視が生きていると誤認したまま作業を進めるリスクが減ります。

## 注意点

- コンテナの再起動自体を防ぐものではなく、再起動が発生した際にユーザーへその影響を正しく伝えるための修正です
- 失われたバックグラウンド作業は自動的には復元されないため、必要な場合は再実行が必要です
