## 原文（日本語訳）

Bashサンドボックスのコマンド実行後クリーンアップ処理が、`~/.claude/settings.json` がサンドボックスの書き込み可能領域外を指すシンボリックリンク（nix/home-managerやstowなどdotfile管理ツールによるもの）に張り替えられている場合、そのシンボリックリンクを削除してしまう問題を修正しました。

## 原文（英語）

Fixed the Bash sandbox's after-command cleanup deleting a dotfile-managed `~/.claude/settings.json` symlink (nix/home-manager, stow) when it is repointed outside the sandbox's writable area

## 概要

Bashサンドボックス機能は、コマンド実行時に発生した意図しないファイル変更を検知・後始末するためのクリーンアップ処理を持っています。nix/home-managerやGNU stowのようなdotfile管理ツールを使っていると、`~/.claude/settings.json` は実体ファイルではなくサンドボックスの書き込み可能領域外（Nixストアなど）を指すシンボリックリンクになっていることがあります。この修正前は、そのようなシンボリックリンク自体をクリーンアップ対象と誤認識し、削除してしまうことがありました。結果として、dotfile管理システムが管理しているリンクが失われ、設定の再リンクや復旧作業が必要になっていました。

## 基本的な使い方

ユーザー側の操作は不要です。nix/home-managerやstowなどで `~/.claude/settings.json` をシンボリックリンクとして管理している場合でも、Bashツールを使ったコマンド実行後にそのリンクが誤って削除されることがなくなりました。

```bash
# 例: home-managerでシンボリックリンクとして管理されているケース
ls -la ~/.claude/settings.json
# ~/.claude/settings.json -> /nix/store/.../settings.json
```

## 実践例

### home-managerでdotfileを管理している場合

NixOSやhome-managerでホームディレクトリの設定ファイルを宣言的に管理している開発者は、Claude Codeがサンドボックス内でBashコマンドを実行した後も、`settings.json` へのシンボリックリンクがそのまま保持されます。

### GNU stowでdotfileリポジトリを運用している場合

dotfileリポジトリをstowでシンボリックリンクとして展開している場合も同様に、リンク先がサンドボックスの書き込み可能領域外にあっても削除対象にならず、安心してBash実行系のサンドボックスを利用できます。

### 複数マシンでの設定同期運用

複数のマシンで同じdotfileリポジトリを使って設定を同期している場合、意図せずリンクが失われて設定がデフォルトに戻ってしまうといった事故を防げます。

## 注意点

- この問題はシンボリックリンクの参照先がサンドボックスの書き込み可能領域の外にある場合に限られていました
- サンドボックスのクリーンアップ処理自体は、コマンド実行によって作られた本来削除すべき一時ファイルなどには引き続き適用されます
- Bashサンドボックスの詳細な挙動や制限については公式ドキュメントを参照してください
